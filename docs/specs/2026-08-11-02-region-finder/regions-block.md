The `json-regions` data block is where a document keeps the regions found in it, and the `regions` DuckDB table is what falls out of that block when the file syncs. This file owns the stored shape: the Zod schema, the registry entry, and the projection. Everything else in the feature either writes this shape ([detection.md](detection.md) produces it, [region-sync.md](region-sync.md) writes it) or reads it ([decoration.md](decoration.md), [editor-regions.md](editor-regions.md)); the kind vocabulary the `kind` field draws from belongs to [kinds.md](kinds.md).

## Contract

The block is a singleton per document holding two top-level fields. `regions` is an array whose elements are the stored rows below. `scanned` is a record keyed by kind id, each entry listing the scan units (below) `find` has already run over for that kind; [region-sync.md](region-sync.md) owns when entries are written and when they are dropped. It exists because a kind that finds nothing in a document produces no rows at all, so the rows alone cannot distinguish "scanned, found nobody" from "never scanned" — without the record, every session re-scans the whole corpus.

The second field is free at both boundaries, which is why it can be added without disturbing anything below. `rowPath: "regions"` means the projection takes the array *element* and never the wrapper, so `scanned` cannot reach DuckDB, cannot add a column, and cannot add a table. And `recoverArrayItems` (in `app/lib/data-blocks/query.ts`) empties every top-level array key before re-parsing, so what has to parse on its own is `{ "regions": [], "scanned": … }` — which it does, leaving the item recovery below exactly as it was: one bad entry costs one entry rather than the whole block.

Spans are sentence indexes into `indexFileSentences(raw)` from `app/lib/text/halo.ts` — the prose-extracted, markdown-stripped, JSON-blocks-removed sentence array the halo machinery behind deep analysis already indexes. That the array excludes fenced blocks is load-bearing here and not incidental: writing this block into the document does not shift a single index in it.

**Indexes are 0-based array positions.** The first sentence of a document is `0`, and `indexFileSentences(raw)[startSentence]` is a region's first sentence with no arithmetic in between. This file owns the fields, so it owns the base, and it is stated once here rather than four times: [decoration.md](decoration.md) and [editor-regions.md](editor-regions.md) use the stored numbers as array positions directly, and [detection.md](detection.md) converts at its model boundary — it renders 1-based numbering into the prompt, because a model counting from zero is a failure mode bought for nothing, and parses back to 0-based before any value it produces reaches this shape. That is the only conversion in the feature, and it happens on one side of one call.

### The scan unit

A **scan unit** is a contiguous run of rows of that canonical array, accumulated up to `CHUNK_CHARS` and never splitting a sentence. It is the unit one `find` runs over, and it is cut from the canonical array rather than from a second derivation of the document, so a unit boundary is a sentence index and there is no offset in another space to map back from.

The budget is stated in characters because characters are the only measure to hand: `CHUNK_CHARS` (`app/lib/embeddings/constants.ts`) is `CHUNK_TOKENS * CHARS_PER_TOKEN`, 1000 characters, and it is the form `CHUNK_TOKENS` reaches the embedding chunker in — the chunker counts no tokens, and the repo exports no token counter, `estimateTokens` being private to `app/lib/text/excerpt.ts`. So the measure is characters of the unit's sentence texts joined by a single space, the way the hash below joins them, and the rule it makes checkable is that no unit exceeds the budget unless it holds a single sentence that does.

Each entry under a kind id in `scanned` is therefore a pair: the unit's **hash** — `fnvHash` over its sentence texts joined by a single space, the `rangeHash` recipe below applied to a different range — and the **index of its first sentence at the time it was scanned**. The recipe is part of the contract for the reason `rangeHash`'s is: the writer and the re-deriver compute it from different file contents and must agree. The stored index is what the hash alone cannot give. A hash says whether a unit's content survived an edit and nothing about where that content now sits, and the case the index is for is the unit whose hash still matches but whose position moved — the re-cut happened to resynchronise on the same boundary further down, so the identical run of sentences begins at a different index. The hits found in it are still good and only their sentence indexes are stale; the shift that corrects them is the difference between the stored first index and the current one, and without the second half of the pair it is not computable, so those hits would have to be dropped even though nothing about the unit changed. That case is narrower than it may sound, and it is worth saying plainly why: units accumulate greedily from the start of the sentence array, so a sentence inserted upstream generally does re-cut every unit below it — their composition changes, their hashes change, and they are re-found regardless of what was stored. Marks relocate by `rangeHash`, which is computed over a region's own range and is indifferent to where unit boundaries fall, so the expensive `mark` call is spared either way.

Unitting this way rather than by `chunkFileForEmbedding` takes nothing from the rule that it is the only sanctioned chunker: that rule exists so hashes and offsets line up across embeddings, search and deep analysis, and nothing here produces an embedding or writes into a hash space any of them read. What this feature needs is the opposite property — a unit whose hash and whose boundaries are expressed in the coordinate system every stored index already uses.

### The stored row

Without it a value belongs to no layer, and the rule that same-kind regions never overlap has nothing to be stated over.                                 |

| `rangeHash`     | string, optional — `fnvHash` of the range   | [region-sync.md](region-sync.md) on re-derive                                                          | The only identity that survives an edit. Drop it and any edit anywhere in the file invalidates every mark, which costs two LLM calls per document per keystroke burst.    |

`rangeHash` is `fnvHash` (`app/lib/utils/hash.ts`, the same function `hashChunk` wraps for embeddings) over the texts of sentences `startSentence` through `endSentence` inclusive, taken from `indexFileSentences(raw)`, joined by a single space. The recipe is part of the contract because the writer and the re-deriver compute it at different times from different file contents and must agree. The hash covers content and not position, which is exactly what lets a mark survive an edit above it.

Rows sit in one canonical order, and that order is part of the stored shape rather than the writer's habit: by `kind` in `REGION_KIND_IDS` order (registry declaration order, what [kinds.md](kinds.md) pins, and for the shipped kinds `speaker` then `date` rather than alphabetical), then by first sentence index — `startSentence`, or `hitSentence` for a row with no range — then by `hitSentence`. Each `scanned` entry lists its units in first-sentence order under its kind id. The order has to be pinned somewhere because the sync re-derives the whole block and writes only when the result differs from what is on disk; two orderings of the same regions are the same data and a different file, so an unpinned order would show up as a diff on every pass, rewrite every document, and wake the sync that wrote it.

Three fields are absent by decision. `id` — no consumer addresses a region by one, the sync rewrites the block wholesale, and `kind` plus `startSentence` is already unique because same-kind regions never overlap (`kind` plus `hitSentence` for an unresolved occurrence). `actor` — every row here is machine-written, so the column would be a constant. The range's text — recoverable by slicing the sentence array, and storing it would put a second copy of the document inside the document.

### What the schema enforces, and what it refuses to

Enforced, as refinements on the element: `endSentence >= startSentence`; and `startSentence`, `endSentence`, `rangeHash` are all present or all absent. That last one is the answer to whether an occurrence may be stored without a resolved range — it may, and the representation is the absence of those three fields, never a sentinel like `-1` or an empty range. It has to be, because a hit and a mark die independently: deleting a mark must not delete the hit that produced it, and this block is the only place a hit is kept. A range-less row is exactly how a surviving hit is stored, and two components produce one. [detection.md](detection.md) records an unresolved occurrence when `mark` fails rather than fabricating a region the model never bounded. [region-sync.md](region-sync.md) deletes a mark whose range content changed while leaving its hit alive for re-marking. Either way the occurrence stays located, so re-marking costs no second `find` and the sync never has to look for it again. Readers treat a row with a null range as enclosing no text: [decoration.md](decoration.md) matches nothing against it and [editor-regions.md](editor-regions.md) draws no span. When such a row is written and when it stops being worth keeping is [region-sync.md](region-sync.md)'s; admitting it is this schema's job.

Not enforced: that `parsed.type` agrees with the value type its `kind` declares. The kind is the authority on that, every consumer that needs the value type reads it from the descriptor, and a refine here would only police a redundancy the schema itself introduced — at the price of dropping a row whose value and range are perfectly good.

Not enforced either: that indexes fall inside the document. The schema has no document, and `getBlock` is called with content alone. A block whose indexes run past the end of the sentence array is not invalid, it is stale — the ordinary consequence of an edit that landed before the sync ran, and the DB will hold those indexes for as long as the debounce lasts. Readers must tolerate it: containment against a range that overlaps no sentence yields nothing, and rendering clamps to the last sentence. Repair is the sync's re-derive, which finds the run matching `rangeHash` and refreshes the indexes, or deletes the mark when no run matches. And not that `hitSentence` falls within the range, because trailing attribution can sit outside the sentences it owns.

A region whose `kind` is no longer registered fails the element parse, because `kind` is an enum built from the kind registry rather than a bare string. `recoverArrayItems` then drops that one entry with a warning and returns the rest of the block, so an unregistered kind costs its own rows and nothing else. The entry survives on disk, untouched, until the sync next rewrites the block — at which point it is gone. This is the intended trade: a kind that no consumer can render, colour, or type-check is not data anyone can use.

### The derived table

`projected: true` with `rowPath: "regions"` puts each element into a table named `regions` — `stripLanguagePrefix` turns `json-regions` into exactly that, so no `tableName` override. `getRowSchema` resolves the array element into the `ProjectionConfig`'s `schema`, `toJsonSchema` runs `z.toJSONSchema(config.schema, { io: "input" })` over that already-row-resolved schema, and the DDL comes from it and never from runtime data.

| Column          | DuckDB type       |
| :-------------- | :---------------- |
| `file`          | VARCHAR NOT NULL  |
| `kind`          | VARCHAR           |
| `parsed_type`   | VARCHAR           |
| `parsed_value`  | VARCHAR           |
| `quote`         | VARCHAR           |
| `hitSentence`   | INTEGER           |
| `startSentence` | INTEGER           |
| `endSentence`   | INTEGER           |
| `rangeHash`     | VARCHAR           |

Those are the columns this file owns, and the list is not the whole table. `regions` is a projected table like any other, so [decoration.md](decoration.md) extends the row schema with `inferred_meta` and appends its own columns here too — that set is its list to state and to keep current, and this one does not restate it.

`parsed` is a nested object, so it flattens with an underscore prefix, the way annotations' `vote` becomes `vote_find_found`. The row shape contains no array of objects, so `findChildTables` produces nothing and the projection is one table — deliberate, since a child table's only link back is a `file` column and would be unjoinable to the row that spawned it. `parsed_value` is VARCHAR for both kinds: `jsonTypeToDuckDb` maps `format: "date"` to DATE and has no `date-time` case, and one column shared across kinds could not be typed anyway. ISO-8601 sorts and range-compares correctly as text, so ordering still works; the native temporal column lives on decorated blocks and belongs to [decoration.md](decoration.md). Array order is preserved into insert order but SQL guarantees nothing, so a consumer that wants document order sorts by `startSentence` explicitly rather than relying on the block's canonical order surviving into the table.

### Block config, and how the contract is enforced

`schema` is the row shape above wrapped in `{ regions: [...], scanned: {...} }`; `singleton: true`; `projected: true`; `rowPath: "regions"`; `renderer: "hidden"`; `readonly: ["regions", "scanned"]`; `immutable: {}`; `constraints: []`. Deliberately unset: `idPaths` (no ids), `actorPaths` (no actor), `fuzzyFields` (nothing here is text the agent quotes and patches), `normalizeAsFile`, `labelKey`, `captionType`, `allowedFiles`, `asyncValidate`, `patchSchema`, `normalize`.

Parse, don't validate. The Zod schema is the only definition of the shape; the TypeScript type is `z.infer` of it, consumers import that type rather than declaring their own, and the DuckDB columns are generated from it. A block read from disk is hostile text until it has been through `getBlock(raw, "json-regions", schema)` — a user can open the raw markdown and type into it, and multiplayer can deliver anything. There is exactly one door: JSON syntax is caught earlier, at the file store, where `validateStructural` throws `FileCorruptionError` for any malformed `json-*` block; everything structurally valid but wrongly shaped is caught here, at read, by `safeParse` plus item recovery.

Nothing lets the agent write it. `readonly: ["regions", "scanned"]` strips both fields from the model-facing schema `toBlockSchema` builds, so the entry `getBlockSchemaDefinitions()` still contributes to the system prompt names the block and describes no writable property. The actual guarantee is one level down: `json-regions` is absent from `BLOCK_TOOL_LANGUAGES` in `app/lib/agent/tools/block-tools/register.ts`, so no `patch_`, `delete_`, `add_` or `move_` tool is generated for it and the agent has no verb that reaches it — the same arrangement `json-embeddings` already relies on. Neither setting affects the projection or file validation, both of which call `config.schema()` directly.

Side effects at this boundary, all of them consequences of joining the registry rather than of the schema itself. Registering the language makes `validateSemantic` stop rejecting files that contain the block as an unknown data-block language. Declaring it a singleton enrols it in `getSingletonLanguages`, which means `normalizeSingletonOrder` relocates it to the singleton tail on every file write in registry order, and `stripSingletonBlocks` removes it before the topic content hash in `app/domain/data-blocks/attributes/topics/selectors.ts` and before the editor's word count — so writing regions does not trigger reclassification and does not inflate the document's stats. Declaring no `idPaths` keeps it out of `normalizeBlockKeyOrder`'s walk, so the sync's own key order survives on disk unrewritten. Adding a projection changes the DDL, which is `CREATE OR REPLACE TABLE` at boot: a schema change is a rebuild of the corpus, and migrations are not a concept here. The table is exposed, so it appears in `getDatabaseSchema()` and the agent can query it, which is the point of projecting at all. Finally, the parse cache in `query.ts` is keyed on `language:blockContent` without the file, so two documents holding identical region blocks share one parsed object — consumers must treat what `getBlock` returns as frozen and shared, and never mutate a row in place.

## Prior art

`json-annotations` is the near-twin and the thing to copy: a hidden, singleton, projected block with `rowPath` over an array of objects, a schema file separate from its definition file, and an element schema carrying a `.refine` that `z.toJSONSchema` tolerates (its refined element already projects today, which is what makes the refinements above safe). What differs, and why: annotations are written by the agent and by the user, so they carry `id`, `actor`, `fuzzyFields` and a `patchSchema`, and they have `constraints` written as prose for the model; regions are derived output, so all of that is empty and `readonly` covers both top-level fields. Annotations anchor to quoted text that gets fuzzy-matched back into the document; a region's own anchor is sentence indexes plus a content hash, because a region is a run of sentences and not a phrase. Its `quote` is matched back into text in exactly one place — the editor's label — and even there the search runs inside a single sentence the indexes have already identified.

`json-embeddings` (`app/domain/data-blocks/embeddings/definition.ts`) is the precedent for the other half: a programmatic block registered so validation does not warn on an unknown language, kept out of `BLOCK_TOOL_LANGUAGES` so no agent tool exists for it. What is not copied is its projection — embeddings project through a hand-written `embeddingsProjection` with a `fileMapper`, because they live in a companion file. Regions live in the document, so the auto-derived path applies and no entry in `projections.ts` is needed at all.

A companion `.regions.hidden.md` file, embeddings-style, was rejected: the document must carry its own regions so a reload needs no re-query, and a companion would trade the auto-derived projection for a hand-written one plus a file-mapping rule for no gain.

Keying `scanned` by embedding chunk hashes, so the block would record the chunker's own units, was rejected on a mechanical ground rather than a stylistic one. `chunkFileForEmbedding` chunks `extractProse(content)` while `indexFileSentences` splits `stripMarkdown(extractProse(raw), { keepHeadings: true })`: a chunk's text and the sentence rows are two derivations of one document with nothing mapping between them, so a stored chunk hash could never be turned back into the sentence indexes every other field here is written in. `findMatchOffset` cannot bridge them either — `scoreOrderedSubsequence` scores matched tokens against the *needle's* length, so it tolerates extra tokens in the haystack and not in the needle, and `stripMarkdown` deletes tokens (link and image URLs) the chunk still carries; and its window loop cannot run at all when the needle has more tokens than the haystack, which is the case for any document small enough to fit a single chunk — the walking skeleton's own document among them. A hash over a run of canonical sentences needs no bridge, because the rows it hashes are the rows the indexes address.

A child table for the sentence range (one row per sentence in the region) was rejected: `ddl.ts` links a child table to its parent by `file` alone, so the rows could never be joined back to the region that produced them.

## Tests

### Skeleton

The block's piece of the walking skeleton: after the sync writes a `json-regions` block into the one-kind transcript document, the file survives `normalizeFile` unchanged on the next write, `getBlock` parses it, and `SELECT * FROM regions` returns one row per speaker region with `file` equal to the document's path, `kind` of `speaker`, `parsed_value` the picked slug, and `startSentence`/`endSentence` matching the regions the editor drew.

### Contract

Given a block hand-corrupted so one entry is missing `parsed`, when the document is read, then that entry is dropped with a warning and every remaining region still projects — the block does not fail whole.

Given a block whose JSON is truncated mid-array, when the file is written to the store, then the write is refused with `FileCorruptionError` naming the file; and given the same content arriving by a path that bypasses the store, when it is read, then `getBlock` returns null and the file contributes zero rows rather than throwing.

Given a block whose `scanned` names two kinds with several scan units each, when the document is read and projected, then every unit's hash and first sentence index survive the read unchanged, `scanned` produces no column on `regions` and no second table, and a corrupt entry in `regions` alongside it is still recovered singly.

Given a region whose `kind` is not in the kind registry, when the document is read, then only that region is dropped, and given a document of nothing but such regions, then `regions` holds no rows for that file and no error surfaces.

Given a region whose `startSentence` and `endSentence` both exceed the document's sentence count, when the document is read, then the entry parses and projects unchanged, because staleness is not invalidity and only the sync repairs it.

Given a region with `hitSentence` but no `startSentence`, `endSentence` or `rangeHash` — the row [detection.md](detection.md) records when `mark` fails, and the row a hit is left as when [region-sync.md](region-sync.md) deletes its mark — when the document is read, then it parses and projects with three null columns; and given the same region with `startSentence` but no `rangeHash`, then it is dropped, because the range triple is all-or-nothing.

Given a region with `endSentence` less than `startSentence`, when the document is read, then it is dropped.

Given a region on the document's first sentence, when it is read, then its `startSentence` is `0` and `indexFileSentences(raw)[0]` is the sentence it covers — the base is asserted against the real function, not against a number written in a fixture.

Given the projected schema for `json-regions`, when the table projection is built, then a table named `regions` carries every column in the list above with the type stated there, no `regions_*` child table exists, and `parsed` appears as `parsed_type` and `parsed_value` rather than as a column of its own. The assertion is over those columns and that absence, never over the total column count: [decoration.md](decoration.md) appends to this table, and a test that pins the total would fail the day it lands.

Given a document containing a regions block, when it round-trips through `normalizeFile` twice, then the second pass is byte-identical to the first, the block sits in the singleton tail in registry order, and the document's topic content hash is the same as it was before the block existed.

Given two different documents holding byte-identical regions blocks, when both are read, then each projects rows under its own `file` and neither read mutates what the other sees.

### Isolation

The schema and the projection are exercised with no LLM, no editor, no sync and no DuckDB: a fixture markdown string with a hand-written regions block, `getBlock` against the exported schema, and table-driven cases over the resulting rows — one valid, one per rejection above. The projection half needs even less: `jsonSchemaToTableProjection("regions", toJsonSchema(...))` checked for the columns this file owns and for the absence of a child table, and `extractRows` over a literal row object, both pure functions over the static schema. Sentence indexes need no real document to be tested here, since the schema deliberately knows nothing about one; the base case above calls `indexFileSentences` on the fixture directly and asserts the two agree.
